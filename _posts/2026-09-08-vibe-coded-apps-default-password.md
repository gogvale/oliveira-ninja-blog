> **TL;DR** — A weekend founder ships a payment app written entirely by an assistant. 45% of AI-generated code contains a security flaw. The bigger problem: the people shipping it believe it is secure. Escape.tech counted 2,038 high-impact vulnerabilities across vibe-coded production apps. The vibe-coded app is the new admin/admin — and nobody is reading the code.

A founder spends a weekend building a stablecoin on-ramp. Next.js, Supabase, Clerk. Every line generated by an assistant, every line pasted without a second read. The demo is flawless. The production app, less so — the API key in the client bundle, the `service_role` in a committed `.env`, the row-level security left `public`. None of it is exotic. All of it is the same mistake, multiplied by everyone now shipping code they did not write and did not read.

The number that keeps showing up is 45%. [Veracode](https://www.veracode.com/blog/ai-generated-code-security-risks/) measured real development tasks across Copilot, Claude Code and ChatGPT and found 45% of AI-generated code contains a security flaw.

The more interesting number is the confidence gap. [Stanford's study](https://arxiv.org/abs/2211.03622) — the first large-scale one with real users — found that people using an AI assistant wrote significantly *less* secure code and were *more* likely to believe it was secure. The assistant made them feel safer while making their code worse. That false confidence is the actual attack vector: not the model, the operator.

Production confirms the lab. [Escape.tech](https://escape.tech/state-of-security-of-vibe-coded-apps) scanned vibe-coded apps running in production and counted 2,038 high-impact vulnerabilities, 400-plus exposed secrets and 175 personal-data leaks — medical records and bank account numbers among them. And a [Lovable-built app](https://cybernews.com/security/lovable-vibe-coding-flaw-apology/) exposed the source code and database passwords of all its users: 18,697 student records, 4,538 of them minors. The researcher who reported it was ignored for 48 days.

Map those numbers onto the weekend founder's stablecoin app and you get a checklist that requires no sophistication at all:

- a payment API key pasted into the client bundle — [GitHub counted 39 million secrets leaked in 2024 alone](https://github.blog/security/application-security/next-evolution-github-advanced-security/)
- auth and KYC logic that validates permissions wrong — the exact false-confidence pattern Stanford documented
- row-level security left public — the pattern behind those 175 PII leaks
- an unreviewed Sunday-night deploy — the step where every one of the above ships

Every one of these is the digital equivalent of leaving the key in the door. Nobody needs a zero-day. They need you to have skipped the boring parts.

The honest caveat: this is not a story about a malicious model. The same research shows a competent review closes most of the gap — Copilot Chat fixed 55.5% of its own flagged issues in one study. The problem is the process, not the machine. The founder shipping in a weekend does not review. The 80% of developers who skip their organization's AI-code security policies do not scan. The velocity is the vulnerability.

Which is why the vibe-coded app is becoming what the default password used to be. A decade ago the breached small business was running `admin/admin` on a router nobody updated. Today it is running a weekend-built app nobody reviewed. Same root cause: the boring, preventable layer nobody bothers with. Three things would fix most of it — review the code, scan for secrets, keep the keys out of the client. None of them are new. All of them got skipped in the rush to ship.

We spent years telling people to change the default password. We are about to spend years telling them to read the code they did not write.
